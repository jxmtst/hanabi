# ADR-0003: 表示設定はメニューバーから実行時に変更し set-options IPC に一本化する

- Status: Accepted
- Date: 2026-08-29
- Deciders: プロジェクトオーナー

## Context（背景）

hanabi の表示部は Electron（[ADR-0001](0001-use-electron.md)）で、受信部と分離した二層構成（[ADR-0002](0002-two-layer-architecture.md)）である。全画面・完全クリックスルーのオーバーレイのため、画面上に操作 UI は置かず、メニューバー常駐（Tray）を唯一の操作面としている。

当初、表示に関わる設定（表示方式、表示ディスプレイ、文字サイズ、速度、最大表示数、送信者名の表示、アイコンの表示/大きさ、絵文字サイズ）は `.env` に置き、起動時にのみ反映していた。しかし運用の中で「値を試しながら実行中に調整したい」「.env を編集して再起動するのは手間」という要望が明確になった。

論点：
- 実行中に変更したい設定が増えるにつれ、設定ごとに専用の IPC（`set-renderer`, `set-avatar` …）を増やすと表示部・preload・main の三箇所に重複した配線が積み上がる。
- 文字サイズなど、レンダラの幾何（レーン高・レーン数）に影響する設定は、値を差し替えるだけでは既存レンダラに反映されない。

## Decision（決定）

1. **表示に関わる設定はすべてメニューバー（Tray）から実行時に変更可能にする。** `.env` の各値は「起動時の既定値」として残す。
2. **設定変更は汎用の `set-options` IPC に一本化する。** main から `{ 変更キー: 値, ... }` の差分パッチを送り、表示部は共有 `options` を `Object.assign` で更新する。
3. **表示部は options 更新のたびに現在のレンダラを作り直す（`build()`）。** これにより文字サイズなど幾何に関わる設定も確実に反映される。既に表示中の弾幕は各自のタイマーで自然に消える。
4. **表示方式の切替（`set-renderer`）とディスプレイ移動はレンダラ再生成やウィンドウ移動を伴うため個別のまま**とし、options パッチとは分ける。
5. **永続化は行わない（現時点）。** メニューでの変更は実行中のみ有効で、再起動すると `.env` の既定に戻る。

各設定の `.env` 既定値は、メニューのプリセットのいずれかに一致させ、起動直後に選択状態（チェック）が表示されるようにする。

## Consequences（結果）

### Positive（利点）

- 設定を再起動なしで試行錯誤できる。全画面クリックスルーでも Tray だけで完結する。
- 設定追加時の配線が最小化される（main のメニュー項目追加 ＋ `sendOptions({key:value})` のみ。preload/表示部は変更不要）。
- `build()` による作り直しで、幾何に依存する設定も一貫して反映される。実装が単純で状態のズレが起きにくい。

### Negative（欠点・トレードオフ）

- options 変更のたびにレンダラを作り直すため、変更の瞬間にレーン占有状態がリセットされ、ごく短時間だけ弾幕が重なりうる。実用上は許容範囲。
- 変更が永続化されないため、常用の設定は結局 `.env` に書く必要がある。
- 値はプリセット（離散値）からの選択で、任意の数値入力はできない。

### 中立・将来への含み

- 「最後に選んだ設定を次回も使う」需要が出れば、選択内容を設定ファイルへ保存する永続化を別途追加する（本 ADR の 5 を見直す形）。
- スライダー等の連続値 UI が必要になれば、別ウィンドウの設定画面を検討する。

## Alternatives considered（検討した代替案）

### 設定ごとに専用 IPC を増やす

- 利点：各処理が明示的。
- 欠点：設定が増えるほど main・preload・表示部に重複配線が積み上がり、保守コストが増える。実際に `set-avatar` を追加した時点で冗長さが見え始めた。
- 判断：`set-options` への一本化で不採用。

### options を動的参照させ、レンダラを作り直さない

- 利点：作り直しに伴うレーンリセットが起きない。
- 欠点：文字サイズなどレンダラ生成時に確定する幾何（レーン高・レーン数）に反映されない。反映するには結局レンダラ側に再計算ロジックを持たせる必要があり複雑化する。
- 判断：作り直し方式のほうが単純で確実なため不採用。

### GUI 設定画面（別ウィンドウ）を作る

- 利点：連続値やまとまった設定編集がしやすい。
- 欠点：MVP には過剰。全画面クリックスルーの操作面として Tray で足りる。
- 判断：現時点では不採用。将来必要になれば検討。
